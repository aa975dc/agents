# 代码分析智能团 Agent 体系设计

> 对目标软件做全面体检：代码结构、模块划分、整体架构、依赖关系、构建流程。
> 体系格式对齐 `software-dev-swarm-design.md`（制品即接口 / 星型编排 / 闸门硬性化 / 决策三级制）。
> **与开发团队的关键差异**：智能团只读不改——一切产出是"带证据的结论"，不是"变更后的代码"。

---

## 0. 设计起点

| | 单代理一次性分析 | 本设计 |
|---|---|---|
| 角色数 | 1（一个会话从头读到尾） | **8**（总控 + 勘察 + 模块×N + 架构 + 依赖 + 构建 + 验证 + 报告） |
| 大库处理 | 上下文溢出即截断 | **分块并行 + 契约蒸馏 + 黑板共享** |
| 结论可信度 | 无法区分"看到"与"猜到" | **证据强制（file:line）+ 独立交叉验证** |
| 流程终点 | 一篇散文式总结 | **结构化报告 + 覆盖声明 + 未验证区披露** |
| 复用性 | 每次从零重读 | **黑板缓存 + git 增量复析** |

---

## 1. 七条设计原则

1. **制品即接口。** 角色之间不传对话，传类型化制品（JSON/CSV/MD），schema 即契约。
2. **星型编排。** 一切跨角色信息经总控（C0 谋定后）中转，成员之间不直连；点对点澄清是例外通道。
3. **证据强制。** 任何写入报告的结论必须带 `file:line`（或命令输出）+ 严重度 + 置信度。没有证据的判断只能进"待验证"区。
4. **传契约不传代码。** 块间共享的是"接口契约摘要"（≤50 行），不是原始代码。上下文预算只花在自己块的深读上。
5. **闸门硬性化。** 每道闸门是可机械判定的条件（字段齐全 / 证据非空 / 覆盖闭合），不凭感觉放行。
6. **验证独立。** 交叉验证员与被验证者**不共享上下文**——重查，不是复述。refuted 的结论保留并标注，不静默删除。
7. **按需裁剪。** 8 个角色是能力全集，小仓库不跑全套（见第 5 节路由）。

## 2. 角色定义

### 2.1 角色总表

| 代号 | 角色 | 姓名 | 输入制品 | 输出制品 | 触发条件 |
|------|------|------|---------|---------|---------|
| **C0** | 总控编排 | 谋定后 | 用户目标（仓库路径 + 分析意图） | 任务分派、黑板维护、交付总结 | 任何请求 |
| **A1** | 勘察测绘 | 罗经纬 | 仓库根路径 | **manifest.json**（语言统计/入口/构建文件/分块方案） | 任何请求 |
| **A2** | 模块深读 ×N | 郝拆解 | 块文件闭集 + 邻块契约 | **chunk 结果 + 模块卡片 + 接口契约摘要** | G1 通过 |
| **A3** | 架构分析 | 高屋建瓴 → 高屋建 | 合并后的模块清单 + 入口分析 | **architecture.md** | G2 通过 |
| **A4** | 依赖分析 | 纲举目 | manifest + 各块依赖边 + 包清单 | **dependency 报告 + 依赖边表 CSV** | G2 通过 |
| **A5** | 构建流程 | 步就班 | 构建文件 + CI 配置 | **build.md**（管线阶段/工具链/产物/环境） | G2 通过 |
| **A6** | 交叉验证 | 铁证如 | 高价值结论样本 | **verdicts**（confirmed / refuted） | G3 通过 |
| **A7** | 报告撰写 | 文汇章 | 全部黑板产物 + 验证结论 | **analysis-report.md** | G4 通过 |

### 2.2 各角色详细定义

#### C0 谋定后 · 总控编排

- **定位**：编排者不是执行者。**不深读业务代码，不代写任何成员的专业产出。**
- **输入**：用户目标（仓库路径、分析意图、深度要求）
- **输出**：通道选型、任务分派单、黑板目录维护、合并与门禁判定、交付总结
- **自决（L1）**：通道选型（快速/单维/标准/增量/工作流）、分块方案微调、重派决策、门禁判定
- **协商（L2）**：制品不满足 schema 打回；模块命名冲突协调归并
- **升级（L3）**：目标仓库不可读、代码混淆/加壳导致分析不可行、范围超预算需用户裁决
- **硬约束**：所有跨成员信息经其中转；不得跳过闸门；黑板只追加不删除

#### A1 罗经纬 · 勘察测绘

- **定位**：花最少的 token 拿到全局图，产出分块方案。
- **输入**：仓库根路径（绝对路径）
- **输出**：`manifest.json` —— 语言统计、入口文件、构建/工程文件清单、目录树摘要、**分块方案（6~20 块，每块 ≤5k LOC / ≤150 文件）**
- **自决（L1）**：分块边界（先目录、后依赖聚类，最小化跨块边）、块编号、尺寸超限的切分与合并
- **协商（L2）**：无
- **升级（L3）**：仓库为空 / 无法读取 / 明显混淆
- **硬约束**：**不深读业务代码**——只看结构、文件名、入口、统计；分块必须覆盖全部源文件（闭合）

#### A2 郝拆解 · 模块深读（每块一个独立实例）

- **定位**：深读单个分块，把代码变成结构化模块卡片。
- **输入**：本块文件闭集 + 邻块接口契约 + 全局 manifest 摘要
- **输出**：`chunks/<id>.json`（模块卡片、块内依赖边、发现）+ `interfaces/<模块名>.md`（对外契约摘要，≤50 行）
- **自决（L1）**：模块识别粒度、命名（遵循仓库已有命名）、模式识别、发现分级
- **协商（L2）**：发现分块错误（文件归属混乱/块超限）→ 退回 A1（经 C0）
- **升级（L3）**：块内发现明显安全后门/恶意代码迹象
- **硬约束**：**只读块内闭集**，禁止全库漫游（需邻块细节时按契约中的路径定点补读）；**只读不改**；每条结论带 `file:line`

#### A3 高屋建 · 架构分析

- **定位**：从合并产物推导整体架构，**不接触原始代码**。
- **输入**：全部模块卡片 + 入口分析 + 依赖边表
- **输出**：`specialty/architecture.md` —— 分层结构（Mermaid）、架构模式判定 + 判定依据、典型数据流/控制流链路、风格一致性评价
- **自决（L1）**：架构模式判定、分层归属、链路选取
- **协商（L2）**：模块职责重叠/命名冲突 → 报 C0 协调归并
- **升级（L3）**：无
- **硬约束**：**不读原始代码**（金字塔原则：只消费蒸馏产物）；判定必须引用支撑它的模块卡片，不得凭空推断

#### A4 纲举目 · 依赖分析

- **定位**：把"谁依赖谁"变成可计算的图。
- **输入**：manifest + 各块依赖边 + 包清单/锁文件
- **输出**：`specialty/dependency.md` + `graph/internal-deps.csv` + `graph/external-deps.csv` —— 内部耦合热点、循环依赖清单、外部依赖表（版本/用途/许可证/过期/漏洞标记）
- **自决（L1）**：耦合度量口径、热点阈值、图的呈现形式
- **协商（L2）**：接口对不上（边指向不存在的模块）→ 退回 A3/A2
- **升级（L3）**：发现已知高危漏洞依赖（CVE）
- **硬约束**：**不评价业务逻辑正确性**；每条边必须有出处（导入语句/清单条目 `file:line`）

#### A5 步就班 · 构建流程

- **定位**：还原"从源码到产物"的完整管线。
- **输入**：构建/工程文件 + CI 配置 + Dockerfile 等
- **输出**：`specialty/build.md` —— 管线阶段图、工具链及版本、环境差异（dev/ci/prod）、产物清单、代码生成步骤、可复现性评价
- **自决（L1）**：阶段划分口径、只读探测命令（如 `--version`/`--help`/dry-run）
- **协商（L2）**：实际入口与勘察清单不符 → 退回 A1（经 C0）
- **升级（L3）**：**实际执行构建须经 C0 批准且在副本目录进行**（默认只做静态分析）
- **硬约束**：**禁止对目标仓库做任何写操作**；默认不执行构建，只还原声明式流程

#### A6 铁证如 · 交叉验证

- **定位**：独立复核关键结论。**只查证，不产出新结论。**
- **输入**：高价值结论样本（高严重度发现、架构判定、入口判定、循环依赖判定）
- **输出**：`verification/verdicts.json`（每条 claim → confirmed / refuted + 复查笔记）
- **自决（L1）**：抽样范围、复查方法（读码/跑只读命令）
- **协商（L2）**：refuted 结论 → 退回原产出角色（携带驳回理由与证据）
- **升级（L3）**：无
- **硬约束**：**与被验证者零共享上下文**（不复述原论证，从证据出发重查）；每条 verdict 必须有自己的证据

#### A7 文汇章 · 报告撰写

- **定位**：把黑板产物组装成读者能用的报告。**不产生新结论。**
- **输入**：全部黑板制品 + 验证结论 + 覆盖统计
- **输出**：`report/analysis-report.md`（结构见第 7 节）
- **自决（L1）**：排版、图表选择、详略取舍
- **协商（L2）**：发现制品缺口（某章无数据支撑）→ 报 C0 补派
- **升级（L3）**：无
- **硬约束**：**只组织已有结论，不推断新事实**；区分"观察到的事实 / 推断 / 未验证"三种陈述

## 3. 协作与信息流转

### 3.1 制品黑板

黑板位于**当前工作区**（不污染目标仓库），按目标仓库分目录：

```
analysis/<repo名>/
├── manifest.json            # A1 产出：全局图 + 分块方案
├── chunks/
│   └── chunk-XX.json        # A2 产出：每块的模块卡片/边/发现
├── interfaces/
│   └── <模块名>.md           # A2 产出：对外契约摘要（≤50 行）
├── graph/
│   ├── internal-deps.csv    # A4 产出：内部依赖边 u,v,kind,source
│   └── external-deps.csv    # A4 产出：外部依赖 name,version,purpose,license
├── specialty/
│   ├── architecture.md      # A3 产出
│   ├── dependency.md        # A4 产出
│   └── build.md             # A5 产出
├── verification/
│   └── verdicts.json        # A6 产出
└── report/
    └── analysis-report.md   # A7 产出（最终交付物）
```

### 3.2 三条流转纪律

1. **传引用不传正文。** 消息里只出现路径与类型化摘要；大正文一律落黑板。
2. **单写者原则。** 每个制品只由一个角色写入（`chunks/chunk-03.json` 只属于产出它的那个 A2 实例）。想改别人的制品 → 走回流。
3. **追加不删除。** 被推翻的结论移入 `superseded/` 或在 verdicts 中标注 refuted，审计链保留。

### 3.3 回流通道（6 条）

| # | 发现方 | 问题类型 | 退回目标 | 必须携带的证据 |
|---|-------|---------|---------|--------------|
| 1 | A2 深读 | 分块错误（归属混乱 / 块超限） | A1 勘察（经 C0） | 块统计 + 建议再切分方案 |
| 2 | A3 架构 | 模块职责重叠 / 命名冲突 | C0 协调归并 | 冲突的两张模块卡片 |
| 3 | A4 依赖 | 边指向不存在的模块 | A3 / A2 | 具体边 + 出处 |
| 4 | A5 构建 | 实际入口与勘察清单不符 | A1 勘察（经 C0） | 差异对比 |
| 5 | A6 验证 | 结论 refuted | 原产出角色 | 驳回理由 + 复查证据 |
| 6 | A7 报告 | 制品缺口（章节无数据） | C0 补派 | 缺口清单 |

**回流铁律**：指定退回目标 + 携带证据。不允许"这里不对，你们看看"。

## 4. 决策边界：三级模型与决策矩阵

### 4.1 三级定义

| 级别 | 名称 | 行为 | 流程影响 |
|------|------|------|---------|
| **L1** | 自决 | 自己拍板，记录后继续 | 不打断 |
| **L2** | 协商 | 退回对应角色重做，或请 C0 协调 | 局部回环 |
| **L3** | 升级 | 由用户裁决 | **流程暂停等待** |

### 4.2 决策矩阵

| 决策类型 | A1 勘察 | A2 深读 | A3 架构 | A4 依赖 | A5 构建 | A6 验证 | A7 报告 |
|---------|--------|--------|--------|--------|--------|--------|--------|
| 分块方案 · 块边界 | **L1** | L2 | L2 | L2 | L2 | L2 | L2 |
| 模块识别 · 命名 · 模式 | L2 | **L1** | L2 | L2 | L2 | L2 | L2 |
| 架构模式判定 · 分层 | L2 | L2 | **L1** | L2 | L2 | L2 | L2 |
| 耦合度量口径 · 热点阈值 | L2 | L2 | L2 | **L1** | L2 | L2 | L2 |
| 构建阶段划分 · 是否执行构建 | L2 | L2 | L2 | L2 | **L1**（执行须 C0 批） | L2 | L2 |
| 抽样范围 · 结论 confirmed/refuted | L2 | L2 | L2 | L2 | L2 | **L1** | L2 |
| 排版 · 详略取舍 | L2 | L2 | L2 | L2 | L2 | L2 | **L1** |
| 发现上游制品缺陷 → 退回 | L2 | L2 | L2 | L2 | L2 | L2 | L2 |
| 仓库不可读 · 混淆 · 范围超预算 | **L3** | L3 | L2 | L2 | L2 | L2 | L2 |
| 高危安全发现（后门/CVE） | L2 | **L3** | L2 | **L3** | L2 | L2 | L2 |

**读法**：任何角色发现上游缺陷都是 L2（退回，不自己改）；安全红线一律 L3（停下来报告用户）。这两条是骨架。

## 5. 编排与协同方案

### 5.1 工作流路由

| 场景 | 判定条件 | 通道 | 涉及角色 |
|------|---------|------|---------|
| 小仓库 | ≤10 个源文件 | ⚡ 快速通道 | C0 → A1（轻）→ A2 单实例 → A7 |
| 大仓库 | >100 文件 或 >50k LOC | 🌊 工作流通道 | 动态工作流全链路（并行 + 断点恢复 + 进度板） |
| 中型仓库 | 两者之间 | 🏗️ 标准 SOP | 全链路 8 角色 |
| 单维分析 | 只要依赖图 / 只要构建流程 | 📋 单维通道 | C0 → A1 → 对应专项 → A7（轻） |
| 复析已有仓库 | 黑板已存在且目标有 git | 🔄 增量通道 | git 圈变更 → 只重派受影响块 → 重跑 A3~A7 |

**默认倾向**：宁轻勿重。快速通道能解决的绝不跑标准 SOP。

### 5.2 标准 SOP 编排

```
用户目标（仓库路径 + 意图）
  ↓
[A1 勘察测绘] ──manifest──→ ⛩ G1 勘察闭合（分块覆盖全部源文件；块尺寸在预算内；入口/构建文件已标记）
  ↓
[A2 模块深读 ×N 并行] ──chunk 结果──→ ⛩ G2 块结果合格（schema 完整；证据非空；模块名无冲突；契约摘要已写）
  ↓
[A3 架构] ∥ [A4 依赖] ∥ [A5 构建]   ──专项制品──→ ⛩ G3 专项闭合（架构引用的模块都存在；依赖边可归位；构建覆盖全部构建入口）
  ↓
[A6 交叉验证] ──verdicts──→ ⛩ G4 验证完成（抽样结论全部有 verdict；refuted 已回流或标注）
  ↓
[A7 报告撰写] ──analysis-report.md──→ ⛩ G5 报告合格（章节完整；结论带证据；覆盖声明如实）
  ↓
交付总结（C0）
```

**闸门判定标准（可机械判定）**：

| 闸门 | 判定条件 | 不通过时 |
|------|---------|---------|
| G1 勘察闭合 | manifest.chunks 的文件并集 = 源文件全集；每块 ≤5k LOC/≤150 文件；6~20 块 | 打回 A1 调整分块 |
| G2 块结果合格 | 每 chunk JSON 字段齐全；findings 均有 evidence；interfaces/ 有对应契约 | 打回对应 A2 实例（≤2 轮） |
| G3 专项闭合 | 架构引用模块 ∈ 模块全集；依赖边两端可归位；构建文件全覆盖 | 按回流通道 2/3/4 退回 |
| G4 验证完成 | 高严重度结论 + 架构判定 + 入口判定 100% 有 verdict | 补派验证 |
| G5 报告合格 | 报告含全部必备章节；每条结论有证据；未覆盖区显式声明 | 打回 A7 |

### 5.3 快速通道

```
用户目标 → C0 自行普查（glob + 读入口）→ 单个 A2 全读 → A7 组装 → 交付
```

适用：脚本、单页应用、小型 CLI。跳过分块与专项角色，但**证据规则与报告结构不简化**。

### 5.4 单维通道

`/analyze-team D:\repo 只要依赖关系` → A1（轻）→ A4 → A7（仅依赖章节）。其余章节标注"本次未覆盖"。

### 5.5 增量复析

1. 读取既有黑板 `analysis/<repo>/`
2. `git.changedFiles(base)` 圈出变更文件
3. 映射到受影响块 → 只重派这些块（块名不变 → 工作流模式下缓存命中，零成本）
4. 重跑 A3~A7（合并阶段必须全量重算）

### 5.6 并发机会

- A2 各块天然并行（互不依赖，输入在分派时已冻结）
- A3/A4/A5 三个专项并行（都只依赖合并产物）
- A7 必须串行在最后（需要全部产物）

## 6. 制品契约

### 6.1 manifest.json（A1）

```yaml
meta: { target, generated_at, tool: A1 }
languages: { <语言>: <文件数> }
loc_total: int
entry_points: [{ path, why }]                    # why: main/package.json bin/…
build_files: [{ path, kind }]                    # kind: makefile/cmake/webpack/ci/docker/…
```

## 7. 最终报告结构（A7 产出，C0 验收）

```markdown
# 《repo 名》全面分析报告
0. 元信息：分析日期、commit/版本、覆盖统计（块数/文件数/LOC/覆盖率）、通道与方法
1. 执行摘要（≤1 页）：软件做什么、技术栈、规模、架构一句话定性、健康度结论
2. 代码库全景：带注释的目录树、语言构成表
3. 模块清单：每模块一张卡片（职责/入口/接口摘要/依赖/模式/风险）
4. 架构分析：分层图（Mermaid）、模式判定+依据、典型数据流、风格一致性
5. 依赖分析：内部依赖图+耦合热点+循环依赖；外部依赖表（版本/许可证/漏洞标记）
6. 构建流程：管线阶段图、工具链、环境差异、产物、可复现性
7. 发现与风险：按严重度排序，每条带 file:line 证据 + 验证状态（verified/refuted/unverified）
8. 覆盖声明：分析了什么、没分析什么、为什么（绝不留白）
附录：分块方案、验证记录、黑板路径
```

**C0 交付总结（对话中汇报）**：TL;DR 一句话 → 交付概览（覆盖率/发现数/验证率）→ 报告路径 → 3 个下一步建议。

## 8. 与常见做法的差异

| 常见做法 | 本设计 | 为什么 |
|---------|--------|--------|
| 一个会话从头读到尾 | 8 角色分块并行 | 大库必溢出；深度与广度不可兼得 |
| 块间互传代码 | 传契约摘要 | 上下文预算花在刀刃上 |
| 报告=读后感 | 证据强制的结构化报告 | 用户要拿去决策，"我觉得"不算数 |
| 生成即定论 | 独立交叉验证 + refuted 标注 | 模型会幻觉；复核要换上下文才有效 |
| 每次从零重读 | 黑板缓存 + git 增量复析 | 二次分析成本趋近于零 |
| 结论覆盖不明 | 覆盖声明独立成章 | "没找到问题"≠"没找" |

## 9. 大库分块与上下文共享（核心机制）

1. **两阶段扫描**：第一阶段 A1 用脚本化手段（目录遍历、文件统计、git 元数据、导入语句抽样）拿全局图——近零 token；第二阶段 A2 才花预算深读。
2. **契约蒸馏**：每块完成后产出 ≤50 行接口契约；后续块的输入 = 本块全文 + **邻块**契约 + manifest 摘要，绝不携带全库。
3. **金字塔汇总**：块结果 → 合并模块清单 → 专项模型。A3/A4/A5 永不接触原始代码。
4. **闭集派发**：A2 收到的文件清单是闭集，禁止漫游；需要邻块细节按契约路径定点补读。
5. **黑板即缓存**：中断/复析时已完成的块直接复用；工作流模式下块名不变 → Amend 缓存命中。
6. **尺寸红线**：块超限 → A1 对半切（沿内部目录或依赖簇）；<300 LOC 的小块与近邻合并。

## 10. ZCode 落地（文件清单与用法）

```
.analysis-team/
├── DESIGN.md                       # 本文档
├── agents/
│   ├── a1-scout.md                 # 罗经纬 · 勘察测绘
│   ├── a2-module-analyst.md        # 郝拆解 · 模块深读
│   ├── a3-architect.md             # 高屋建 · 架构分析

│   ├── a6-verifier.md              # 铁证如 · 交叉验证
│   └── a7-reporter.md              # 文汇章 · 报告撰写
└── workflow/
    └── code-analysis.dwf.ts        # 动态工作流脚本（大库通道）

.agents/commands/analyze-team.md    # /analyze-team 斜杠命令（C0 操作手册）
```

**两条执行路径**：

| 路径 | 入口 | 适用 | 特点 |
|------|------|------|------|
| A. 斜杠命令 | `/analyze-team <仓库路径> [意图]` | 小/中库 | 主会话当 C0，用 Agent 工具派发，零确认开销 |
| B. 动态工作流 | 已注册为全局工作流 `code-analysis-swarm`（参数 target = 仓库绝对路径） | 大库 | 类型化结果、阶段图审批、断点恢复、进度看板 |

两条路径共用同一套角色提示词与黑板布局，可互相切换。角色提示词以绝对路径引用，工作流在任意工作区运行都能找到同一套角色定义。

### 10.1 跨窗口 / 跨工作区使用

| 场景 | 用法 |
|------|------|
| **任何 ZCode 窗口（任意文件夹）** | 对话里说：「运行已保存的工作流 `code-analysis-swarm`，target 是 `D:\xxx`」。全局注册不挑工作区；报告与黑板落在**当前窗口的工作区** `analysis/<repo名>/` 下 |
| 本默认工作区的窗口 | 直接 `/analyze-team D:\xxx`（斜杠命令原生加载）；也可用上面的工作流方式 |
| 其他文件夹也想要斜杠命令 | 把 `.analysis-team/` 文件夹与 `.agents/commands/analyze-team.md` 复制到那个项目根目录 |
| 任何窗口、不用工作流 | 对话说：「按 `C:\Users\G\.zcode\workspace\default\.analysis-team\DESIGN.md` 的体系作为 C0，分析 `D:\xxx`」——体系与角色提示词都在磁盘上，任何会话读了就能照跑 |

## 11. 已确认决策（2026-09-19）

1. **典型规模：万行级** —— 默认参数即为此调优（6~20 块 × ≤5k LOC/块；万行仓库通常落在 3~6 块）。
2. **不设独立安全角色 A8** —— 安全作为 A2/A4 的发现类别 + L3 升级红线。
3. **报告语言：中文**（代码引用、标识符保持原文）。
4. **工作流已注册为全局**：名 `code-analysis-swarm`，任意 ZCode 窗口可按名运行。
5. **构建默认静态分析**（`executed: false`）；需要真实执行构建时单独授权，在副本目录进行。
