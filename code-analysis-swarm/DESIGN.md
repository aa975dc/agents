# 代码分析智能团 Agent 体系设计

> 对目标软件做全面体检：代码结构、模块划分、整体架构、依赖关系、构建流程。
> 体系格式对齐 `software-dev-swarm-design.md`（制品即接口 / 星型编排 / 闸门硬性化 / 决策三级制）。
> **与开发团队的关键差异**：智能团只读不改——一切产出是"带证据的结论"，不是"变更后的代码"。

---

## 0. 设计起点

| | 单代理一次性分析 | 本设计 |
|---|---|---|
| 角色数 | 1（一个会话从头读到尾） | **8**（总控 + 勘察 + 模块×N + 架构 + 依赖 + 构建 + 验证 + 报告） |
| 大库处理 | 上下文溢出即截断 | **分块并行 + 契约蒸馏 + 黑板共享** |
| 结论可信度 | 无法区分"看到"与"猜到" | **证据强制（file:line）+ 独立交叉验证** |
| 流程终点 | 一篇散文式总结 | **结构化报告 + 覆盖声明 + 未验证区披露** |
| 复用性 | 每次从零重读 | **黑板缓存 + git 增量复析** |

---

## 1. 七条设计原则

1. **制品即接口。** 角色之间不传对话，传类型化制品（JSON/CSV/MD），schema 即契约。
2. **星型编排。** 一切跨角色信息经总控（C0 谋定后）中转，成员之间不直连；点对点澄清是例外通道。
3. **证据强制。** 任何写入报告的结论必须带 `file:line`（或命令输出）+ 严重度 + 置信度。没有证据的判断只能进"待验证"区。
4. **传契约不传代码。** 块间共享的是"接口契约摘要"（≤50 行），不是原始代码。上下文预算只花在自己块的深读上。
5. **闸门硬性化。** 每道闸门是可机械判定的条件（字段齐全 / 证据非空 / 覆盖闭合），不凭感觉放行。
6. **验证独立。** 交叉验证员与被验证者**不共享上下文**——重查，不是复述。refuted 的结论保留并标注，不静默删除。
7. **按需裁剪。** 8 个角色是能力全集，小仓库不跑全套（见第 5 节路由）。

## 2. 角色定义

### 2.1 角色总表

| 代号 | 角色 | 姓名 | 输入制品 | 输出制品 | 触发条件 |
|------|------|------|---------|---------|---------|
| **C0** | 总控编排 | 谋定后 | 用户目标（仓库路径 + 分析意图） | 任务分派、黑板维护、交付总结 | 任何请求 |
| **A1** | 勘察测绘 | 罗经纬 | 仓库根路径 | **manifest.json**（语言统计/入口/构建文件/分块方案） | 任何请求 |
| **A2** | 模块深读 ×N | 郝拆解 | 块文件闭集 + manifest 摘要（并行首轮无冻结邻块契约，见 6.3） | **chunk 结果 + 模块卡片 + 接口契约摘要** | G1 通过 |
| **A3** | 架构分析 | 高屋建瓴 → 高屋建 | 合并后的模块清单 + 入口分析 | **architecture.md** | G2 通过 |
| **A4** | 依赖分析 | 纲举目 | manifest + 各块依赖边 + 包清单 | **dependency 报告 + 依赖边表 CSV** | G2 通过 |
| **A5** | 构建流程 | 步就班 | 构建文件 + CI 配置 | **build.md**（管线阶段/工具链/产物/环境） | G2 通过 |
| **A6** | 交叉验证 | 铁证如 | 高价值结论样本 | **verdicts**（confirmed / refuted / unverified） | G3 通过 |
| **A7** | 报告撰写 | 文汇章 | 经核验存在的黑板制品清单 + 验证结论 + 覆盖统计 | **analysis-report.md** | G4 通过 |

### 2.2 各角色详细定义

#### C0 谋定后 · 总控编排

- **定位**：编排者不是执行者。**不深读业务代码，不代写任何成员的专业产出。**
- **输入**：用户目标（仓库路径、分析意图、深度要求）
- **输出**：通道选型、任务分派单、黑板目录维护、合并与门禁判定、交付总结
- **自决（L1）**：通道选型（快速/单维/标准/增量/工作流）、分块方案微调、重派决策、门禁判定
- **协商（L2）**：制品不满足 schema 打回；模块命名冲突协调归并
- **升级（L3）**：目标仓库不可读、代码混淆/加壳导致分析不可行、范围超预算需用户裁决
- **硬约束**：所有跨成员信息经其中转；不得跳过闸门；黑板只追加不删除

#### A1 罗经纬 · 勘察测绘

- **定位**：花最少的 token 拿到全局图，产出分块方案。
- **输入**：仓库根路径（绝对路径）
- **输出**：`manifest.json` —— 语言统计、入口文件、构建/工程文件清单、目录树摘要、**分块方案（按规模分块，至少 1 块，每块 ≤5k LOC / ≤150 文件）**
- **自决（L1）**：分块边界（先目录、后依赖聚类，最小化跨块边）、块编号、尺寸超限的切分与合并
- **协商（L2）**：无
- **升级（L3）**：仓库为空 / 无法读取 / 明显混淆
- **硬约束**：**不深读业务代码**——只看结构、文件名、入口、统计；分块必须覆盖全部源文件（闭合）

#### A2 郝拆解 · 模块深读（每块一个独立实例）

- **定位**：深读单个分块，把代码变成结构化模块卡片。
- **输入**：本块文件闭集 + 全局 manifest 摘要；并行首轮没有冻结的邻块契约（见 6.3），跨块细节经回流二次读获得
- **输出**：`chunks/<id>.json`（模块卡片、块内依赖边、发现）+ `interfaces/<chunk_id>/<模块名>.md`（对外契约摘要，≤50 行）
- **自决（L1）**：模块识别粒度、命名（遵循仓库已有命名）、模式识别、发现分级
- **协商（L2）**：发现分块错误（文件归属混乱/块超限）→ 退回 A1（经 C0）
- **升级（L3）**：块内发现明显安全后门/恶意代码迹象
- **硬约束**：**只读块内闭集**，禁止全库漫游（需邻块细节时按契约中的路径定点补读）；**只读不改**；每条结论带 `file:line`

#### A3 高屋建 · 架构分析

- **定位**：从合并产物推导整体架构，**不接触原始代码**。
- **输入**：全部模块卡片 + 入口分析 + 依赖边表
- **输出**：`specialty/architecture.md` —— 分层结构（Mermaid）、架构模式判定 + 判定依据、典型数据流/控制流链路、风格一致性评价
- **自决（L1）**：架构模式判定、分层归属、链路选取
- **协商（L2）**：模块职责重叠/命名冲突 → 报 C0 协调归并
- **升级（L3）**：无
- **硬约束**：**不读原始代码**（金字塔原则：只消费蒸馏产物）；判定必须引用支撑它的模块卡片，不得凭空推断

#### A4 纲举目 · 依赖分析

- **定位**：把"谁依赖谁"变成可计算的图。
- **输入**：manifest + 各块依赖边 + 包清单/锁文件
- **输出**：`specialty/dependency.md` + `graph/internal-deps.csv` + `graph/external-deps.csv` —— 内部耦合热点、循环依赖清单、外部依赖表（版本/用途/许可证/过期/漏洞标记）
- **自决（L1）**：耦合度量口径、热点阈值、图的呈现形式
- **协商（L2）**：接口对不上（边指向不存在的模块）→ 退回 A3/A2
- **升级（L3）**：发现已知高危漏洞依赖（CVE）
- **硬约束**：**不评价业务逻辑正确性**；每条边必须有出处（导入语句/清单条目 `file:line`）

#### A5 步就班 · 构建流程

- **定位**：还原"从源码到产物"的完整管线。
- **输入**：构建/工程文件 + CI 配置 + Dockerfile 等
- **输出**：`specialty/build.md` —— 管线阶段图、工具链及版本、环境差异（dev/ci/prod）、产物清单、代码生成步骤、可复现性评价
- **自决（L1）**：阶段划分口径、只读探测命令（如 `--version`/`--help`/dry-run）
- **协商（L2）**：实际入口与勘察清单不符 → 退回 A1（经 C0）
- **升级（L3）**：**实际执行构建须经 C0 批准且在副本目录进行**（默认只做静态分析）
- **硬约束**：**禁止对目标仓库做任何写操作**；默认不执行构建，只还原声明式流程

#### A6 铁证如 · 交叉验证

- **定位**：独立复核关键结论。**只查证，不产出新结论。**
- **输入**：高价值结论样本（高严重度发现、架构判定、入口判定、循环依赖判定）
- **输出**：`verification/verdicts.json`（每条 claim → confirmed / refuted / unverified + 复查笔记）
- **自决（L1）**：抽样范围、复查方法（读码/跑只读命令）
- **协商（L2）**：refuted 结论 → 退回原产出角色（携带驳回理由与证据）
- **升级（L3）**：无
- **硬约束**：**与被验证者零共享上下文**（不复述原论证，从证据出发重查）；每条 verdict 必须有自己的证据

#### A7 文汇章 · 报告撰写

- **定位**：把黑板产物组装成读者能用的报告。**不产生新结论。**
- **输入**：全部黑板制品 + 验证结论 + 覆盖统计
- **输出**：`report/analysis-report.md`（结构见第 7 节）
- **自决（L1）**：排版、图表选择、详略取舍
- **协商（L2）**：发现制品缺口（某章无数据支撑）→ 报 C0 补派
- **升级（L3）**：无
- **硬约束**：**只组织已有结论，不推断新事实**；区分"观察到的事实 / 推断 / 未验证"三种陈述

## 3. 协作与信息流转

### 3.1 制品黑板

黑板位于 `output_root/run_id/`（两个参数均可选：缺省时 helper 在宿主 workspace 下生成 `.code-analysis-swarm-runs/<随机 run_id>`），必须在目标仓库和插件安装目录之外。每次使用新 run_id，解析真实路径检查符号链接，并排他创建运行目录；发现重名就停止，禁止覆盖。预检与制品/报告核验由 `scripts/precheck.py`（plan/acquire/verify/check-files/read-report）经 world.run 固定 argv 确定性执行，不把模型回报视为文件系统沙箱。

```
<output_root>/<run_id>/
├── manifest.json            # A1 产出：全局图 + 分块方案
├── chunks/
│   └── chunk-XX.json        # A2 产出：每块的模块卡片/边/发现
├── interfaces/
│   └── <chunk_id>/<模块名>.md           # A2 产出：对外契约摘要（≤50 行）
├── graph/
│   ├── internal-deps.csv    # A4 产出：内部依赖边 u,v,kind,source
│   └── external-deps.csv    # A4 产出：外部依赖 name,version,purpose,license
├── specialty/
│   ├── architecture.md      # A3 产出
│   ├── dependency.md        # A4 产出
│   └── build.md             # A5 产出
├── verification/
│   └── verdicts.json        # A6 产出
└── report/
    └── analysis-report.md   # A7 产出（最终交付物）
```

### 3.2 三条流转纪律

1. **传引用不传正文。** 消息里只出现路径与类型化摘要；大正文一律落黑板。
2. **单写者原则。** 每个制品只由一个角色写入（`chunks/chunk-03.json` 只属于产出它的那个 A2 实例）。想改别人的制品 → 走回流。
3. **追加不删除。** 被推翻的结论移入 `superseded/` 或在 verdicts 中标注 refuted，审计链保留。

### 3.3 回流通道（6 条）

| # | 发现方 | 问题类型 | 退回目标 | 必须携带的证据 |
|---|-------|---------|---------|--------------|
| 1 | A2 深读 | 分块错误（归属混乱 / 块超限） | A1 勘察（经 C0） | 块统计 + 建议再切分方案 |
| 2 | A3 架构 | 模块职责重叠 / 命名冲突 | C0 协调归并 | 冲突的两张模块卡片 |
| 3 | A4 依赖 | 边指向不存在的模块 | A3 / A2 | 具体边 + 出处 |
| 4 | A5 构建 | 实际入口与勘察清单不符 | A1 勘察（经 C0） | 差异对比 |
| 5 | A6 验证 | 结论 refuted | 原产出角色 | 驳回理由 + 复查证据 |
| 6 | A7 报告 | 制品缺口（章节无数据） | C0 补派 | 缺口清单 |

**回流铁律**：指定退回目标 + 携带证据。不允许"这里不对，你们看看"。

## 4. 决策边界：三级模型与决策矩阵

### 4.1 三级定义

| 级别 | 名称 | 行为 | 流程影响 |
|------|------|------|---------|
| **L1** | 自决 | 自己拍板，记录后继续 | 不打断 |
| **L2** | 协商 | 退回对应角色重做，或请 C0 协调 | 局部回环 |
| **L3** | 升级 | 由用户裁决 | **流程暂停等待** |

### 4.2 决策矩阵

| 决策类型 | A1 勘察 | A2 深读 | A3 架构 | A4 依赖 | A5 构建 | A6 验证 | A7 报告 |
|---------|--------|--------|--------|--------|--------|--------|--------|
| 分块方案 · 块边界 | **L1** | L2 | L2 | L2 | L2 | L2 | L2 |
| 模块识别 · 命名 · 模式 | L2 | **L1** | L2 | L2 | L2 | L2 | L2 |
| 架构模式判定 · 分层 | L2 | L2 | **L1** | L2 | L2 | L2 | L2 |
| 耦合度量口径 · 热点阈值 | L2 | L2 | L2 | **L1** | L2 | L2 | L2 |
| 构建阶段划分 · 是否执行构建 | L2 | L2 | L2 | L2 | **L1**（执行须 C0 批） | L2 | L2 |
| 抽样范围 · 结论 confirmed/refuted/unverified | L2 | L2 | L2 | L2 | L2 | **L1** | L2 |
| 排版 · 详略取舍 | L2 | L2 | L2 | L2 | L2 | L2 | **L1** |
| 发现上游制品缺陷 → 退回 | L2 | L2 | L2 | L2 | L2 | L2 | L2 |
| 仓库不可读 · 混淆 · 范围超预算 | **L3** | L3 | L2 | L2 | L2 | L2 | L2 |
| 高危安全发现（后门/CVE） | L2 | **L3** | L2 | **L3** | L2 | L2 | L2 |

**读法**：任何角色发现上游缺陷都是 L2（退回，不自己改）；安全红线一律 L3（停下来报告用户）。这两条是骨架。

## 5. 编排与协同方案

### 5.1 工作流路由

| 场景 | 判定条件 | 通道 | 涉及角色 |
|------|---------|------|---------|
| 小仓库 | ≤10 个源文件 | ⚡ 快速通道 | C0 → A1（轻）→ A2 单实例 → A7 |
| 大仓库 | >100 文件 或 >50k LOC | 🌊 工作流通道 | 动态工作流全链路（并行 + 断点恢复 + 进度板） |
| 中型仓库 | 两者之间 | 🏗️ 标准 SOP | 全链路 8 角色 |
| 单维分析 | 只要依赖图 / 只要构建流程 | 📋 单维通道 | C0 → A1 → 对应专项 → A7（轻） |
| 复析已有仓库 | 黑板已存在且目标有 git | 🔄 增量通道 | git 圈变更 → 只重派受影响块 → 重跑 A3~A7 |

**默认倾向**：宁轻勿重。快速通道能解决的绝不跑标准 SOP。

### 5.2 标准 SOP 编排

```
用户目标（仓库路径 + 意图）
  ↓
[A1 勘察测绘] ──manifest──→ ⛩ G1 勘察闭合（分块覆盖全部源文件；块尺寸在预算内；入口/构建文件已标记）
  ↓
[A2 模块深读 ×N 并行] ──chunk 结果──→ ⛩ G2 块结果合格（schema 完整；证据非空；模块名无冲突；契约摘要已写）
  ↓
[A3 架构] ∥ [A4 依赖] ∥ [A5 构建]   ──专项制品──→ ⛩ G3 专项闭合（架构引用的模块都存在；依赖边可归位；构建覆盖全部构建入口）
  ↓
[A6 交叉验证] ──verdicts──→ ⛩ G4 验证状态闭合（全部送验结论有 verdict；refuted 保留，unverified 明示）
  ↓
[A7 报告撰写] ──analysis-report.md──→ ⛩ G5 报告合格（章节完整；结论带证据；覆盖声明如实）
  ↓
交付总结（C0）
```

**闸门目标**（当前 DWF 对第 6 节的返回字段做机械检查；文件内容及证据真实性仍需宿主核对）：

| 闸门 | 判定条件 | 不通过时 |
|------|---------|---------|
| G1 勘察闭合 | manifest.chunks 的文件并集 = 源文件全集；每块 ≤5k LOC/≤150 文件；按规模分块，不截断 | blocked（A1 勘察完整性问题不回流） |
| G2 块结果合格 | 每 chunk JSON 字段齐全（含 from_contract 可选布尔，缺省 false）；findings 均有 evidence；interfaces/ 有对应契约且经 helper 核验真实存在 | 携带具体失败原因重问同一 A2 实例（初次+2 次修复尝试）；路径越界或同错复发直接 blocked |
| G3 专项闭合 | 架构引用模块 ∈ 模块全集；依赖边两端可归位；构建文件全覆盖；specialty/*.md 与 graph/*.csv 经核验真实落盘 | 按回流通道 2/3/4 携带原因退回（≤2 次修复尝试） |
| G4 验证完成 | 送验结论 100% 有独立 verdict（claims 落盘后由工作流经 helper 逐批领取，按批多次 ask 同一 A6 实例，每 ask 载荷 ≤1 批）；无法复查单列 unverified；verdicts.json 落盘 | 每批携带原因重问同一 A6 实例（各 ≤2 次修复尝试）；批数超上限走预算暂停——已复核批次采纳、剩余记 unverified 并列入未覆盖 |
| G5 报告合格 | 报告含全部必备章节；每条结论有证据；未覆盖区显式声明；只引用已核验存在的制品 | 打回 A7（≤2 次修复尝试） |

**有限回流纪律（DWF 已实现）**：可修复类失败（schema 字段缺失/格式、覆盖缺项、模块名/边端点不闭合、声明制品未落盘）按代理实例记账，最多"初次 + 2 次修复尝试"，每次携带具体失败原因重问同一实例（agent 名稳定，上下文续接）；硬阻断类（路径逃逸、权限、未知副作用、与上一次完全相同的失败复发）立即 blocked。**blocked 不抹成果**：已完成 G4 的 confirmed findings/claims 保留在返回值（`claim_verdicts`），并发布"部分完成"报告（artifact `partial-report`），缺口清单显式列出。

### 5.3 快速通道

```
用户目标 → A1 轻量普查 → 单个 A2 全读 → A6 验证关键结论 → A7 组装 → 交付
```

适用：脚本、单页应用、小型 CLI。跳过分块与专项角色，但**证据规则与报告结构不简化**。

### 5.4 单维通道

`/swarm-analyze D:\repo 只要依赖关系` → A1（轻）→ A4 → A7（仅依赖章节）。其余章节标注"本次未覆盖"。

### 5.5 增量复析

1. 读取指定旧 run_id 的黑板，新结果写入全新 run_id。
2. 用真实只读 Git 差异（含未提交/未跟踪状态）圈出变更文件，不依赖未验证的宿主 API。
3. 映射到受影响块；仅在目标真实路径、文件内容指纹、角色/契约版本和依赖均匹配时复用旧制品。当前 DWF 实现全量重跑，尚无可信增量缓存。
4. 重跑 A3~A7（合并阶段必须全量重算）

### 5.6 并发机会

- A2 各块天然并行（互不依赖，输入在分派时已冻结）
- A3/A4/A5 三个专项并行（都只依赖合并产物）
- A7 必须串行在最后（需要全部产物）

## 6. 制品契约

### 6.1 manifest.json（A1）

所有落盘 JSON 和 DWF 返回 JSON 统一使用 snake_case；不能省略覆盖字段。

```yaml
meta: { target, generated_at, tool: A1 }
scan_status: complete|empty|unreadable|partial
scan_evidence: "真实枚举工具/命令及结果摘要"
source_files: [本次范围内全部源文件绝对路径]
excluded: [{ path, reason }]
languages: { <语言>: <文件数> }
loc_total: int
entry_points: [{ path, why, evidence }]
build_files: [{ path, kind }]
tree_summary: string
chunks: [{ id, files: [绝对路径], loc_est, neighbors: [块id], rationale }]
```

G1 检查 scan_status=complete、源文件非空、路径及块 ID 无重复、文件闭集与 source_files 严格相等、块尺寸达标。empty/unreadable/partial 均停止，不宣称“已确认空仓库”。source_files 的真实性仍依赖实际扫描证据。

### 6.2 chunks/chunk-XX.json（A2）

```yaml
meta: { chunk_id, author: "A2:实例" }
modules:
  - { name, responsibility, entry_files: [path], public_interfaces: [签名摘要],
      depends_on: [模块名], patterns: [...], contract_path: 绝对路径 }
edges: [{ from, to, kind: import|call|config, from_contract: bool（可选，缺省 false）, source: "path:line" }]
findings:
  - { id: "chunk-id:序号", where: "path:line", what, evidence,
      severity: low|medium|high, confidence: 0~1 }
coverage: { files_claimed: int, files_analyzed: int, analyzed_files: [完整深读路径], gaps: [原因] }
```

G2 核对计数与逐文件名单，重复、遗漏、抽样阅读和 gaps 均不放行；`from_contract` 为可选布尔（缺省 false，来自邻块契约的跨块边标 true），类型不符按可修复回流处理。模块名必须跨块唯一，依赖端点必须属于模块全集，每条边有来源。chunk JSON 与 interfaces 契约文件经 helper 确定性核验真实落盘，缺失按可修复回流退回对应 A2 实例。

### 6.3 interfaces/<chunk_id>/<模块名>.md（A2）

≤50 行：职责、导出签名、依赖、典型用法。按块划分命名空间防止并行覆盖，contract_path 必须位于本块目录。并行首次深读不依赖尚未冻结的邻块产物；需要补读时由 C0 调度新一轮，不能用竞态决定输入。

### 6.4–6.6 专项文档（A3/A4/A5）

各角色提示词保留架构、依赖、构建的领域结构。构建默认 `executed: false`；未执行构建不等于构建通过。依赖版本/漏洞状态无法查实时标记未知，不能从版本老旧推导 CVE 已确认。

### 6.7 verification/verdicts.json（A6）

落盘和返回统一为对象：

```yaml
verdicts:
  - { claim_id, verdict: confirmed|refuted|unverified,
      note: "独立复查方法或无法复查的原因", own_evidence: "自己的 file:line 或工具输出" }
```

每个送验 ID 恰好对应一次 verdict，不截取前 N 条。confirmed/refuted 都需要独立证据；证据不足属于 unverified。refuted 保留原始记录与反证，不能改成未验证而丢失判定。

分页语义（Z08）：A6 不在一次 ask 中接收全部送验结论——工作流经 helper `claims-page` 逐批领取，按批多次 ask 同一 A6 实例（上下文续接），每 ask 载荷 ≤1 批（80 条），每批返回该批 verdicts，合并后按送验全集闭合。批数超过 50 时预算暂停：已复核批次照常采纳，剩余条目由工作流如实记 unverified（"A6 分页超上限，未复核"）并写入 not_covered，此时 verdicts.json 仅含已复核批次，报告状态为 partial。

### 6.8 report/analysis-report.md（A7）

按第 7 节组织报告。A7 的任务参数只提供经 helper 核验真实存在的黑板制品清单（manifest/chunks/interfaces/specialty/graph/verdicts），清单之外的文件不得作为报告素材。DWF 返回 `{path, summary, sections: [0,1,2,3,4,5,6,7,8], claim_ids: [全部送验ID]}`。运行时检查声明和发布路径；对落盘正文的独立核对仍需真实宿主验收，不将结构检查等同于事实验证。blocked 结局时若 G4 已完成，confirmed 结论以"部分完成"报告（partial-report）保留发布。

### 6.9 专项共同返回摘要（A3/A4/A5）

```yaml
summary: string
details: [string]
findings: [与 6.2 相同，id 使用角色前缀]
claims: [{ id: "A3/A4/A5:序号", claim, source_role, evidence_refs: [非空证据引用] }]
module_refs: [文中引用的模块名]
build_files_covered: [本专项实际检查的构建文件绝对路径]
not_covered: [未完成维度及原因]
```

G3 检查引用存在、架构判定进入送验、A5 构建文件覆盖闭合；专项 md 与依赖 CSV 声明产出后经 helper 核验真实落盘，缺失按可修复回流退回产出角色。G4 自动加入全部入口判定、全部高严重度发现和全部专项 claims（`source_role` 为角色名 A1/A2/A3/A4/A5，finding id 保留在 claim id 中），无数量截断。存在 unverified 或专项缺口则本次状态为 partial。

## 7. 最终报告结构（A7 产出，C0 验收）

```markdown
# 《repo 名》全面分析报告
0. 元信息：分析日期、commit/版本、覆盖统计（块数/文件数/LOC/覆盖率）、通道与方法
1. 执行摘要（≤1 页）：软件做什么、技术栈、规模、架构一句话定性、健康度结论
2. 代码库全景：带注释的目录树、语言构成表
3. 模块清单：每模块一张卡片（职责/入口/接口摘要/依赖/模式/风险）
4. 架构分析：分层图（Mermaid）、模式判定+依据、典型数据流、风格一致性
5. 依赖分析：内部依赖图+耦合热点+循环依赖；外部依赖表（版本/许可证/漏洞标记）
6. 构建流程：管线阶段图、工具链、环境差异、产物、可复现性
7. 发现与风险：按严重度排序，每条带 file:line 证据 + 验证状态（verified/refuted/unverified）
8. 覆盖声明：分析了什么、没分析什么、为什么（绝不留白）
附录：分块方案、验证记录、黑板路径
```

**C0 交付总结（对话中汇报）**：TL;DR 一句话 → 交付概览（覆盖率/发现数/验证率）→ 报告路径 → 3 个下一步建议。

## 8. 与常见做法的差异

| 常见做法 | 本设计 | 为什么 |
|---------|--------|--------|
| 一个会话从头读到尾 | 8 角色分块并行 | 大库必溢出；深度与广度不可兼得 |
| 块间互传代码 | 传契约摘要 | 上下文预算花在刀刃上 |
| 报告=读后感 | 证据强制的结构化报告 | 用户要拿去决策，"我觉得"不算数 |
| 生成即定论 | 独立交叉验证 + refuted 标注 | 模型会幻觉；复核要换上下文才有效 |
| 每次从零重读 | 黑板缓存 + git 增量复析 | 二次分析成本趋近于零 |
| 结论覆盖不明 | 覆盖声明独立成章 | "没找到问题"≠"没找" |

## 9. 大库分块与上下文共享（核心机制）

1. **两阶段扫描**：第一阶段 A1 用脚本化手段（目录遍历、文件统计、git 元数据、导入语句抽样）拿全局图——近零 token；第二阶段 A2 才花预算深读。
2. **契约蒸馏**：每块完成后产出 ≤50 行接口契约；后续块的输入 = 本块全文 + **邻块**契约 + manifest 摘要，绝不携带全库。
3. **金字塔汇总**：块结果 → 合并模块清单 → 专项模型。A3 不接触原始代码；A4/A5 可定点读取依赖清单、锁文件与构建配置。
4. **闭集派发**：A2 收到的文件清单是闭集，禁止漫游；需要邻块细节按契约路径定点补读。
5. **黑板保留证据**：不凭块名复用结果；当前 DWF 全量重跑并使用新 run_id，增量缓存留待内容指纹与依赖失效机制实现。
6. **尺寸红线**：块超限 → A1 对半切（沿内部目录或依赖簇）；<300 LOC 的小块与近邻合并。

## 10. ZCode 落地与兼容性边界

```
code-analysis-swarm/
├── .zcode-plugin/plugin.json
├── DESIGN.md
├── agents/                  # 七个带 name/description 的角色
├── command/swarm-analyze.md       # /swarm-analyze 入口
└── workflow/code-analysis.dwf.ts
```

`plugin.json` 注册 command 与 agents 组件，格式依据 [ZCode 官方插件文档](https://zcode.z.ai/cn/docs/plugin)。命令运行前确定插件安装目录 team_root；只有宿主实际解析安装路径时才使用 `${ZCODE_PLUGIN_ROOT}`，命令正文不能假定该变量会插值。无法取得安装路径时要求明确目录，禁止硬编码某台机器路径。

DWF 为可选执行路径，参数为 target、team_root（必传）与 output_root、run_id（可选，缺省由 helper 生成），返回值统一 snake_case（`gate_checks` 为结构闸门通过记录，≠事实已核verified；事实核验结果见 `findings[].status` 与 `claim_verdicts`）。工作流文件不会因为插件安装而自动全局注册；本仓库不宣称已经在当前 ZCode 环境注册或验证。没有 DWF 时依命令执行手动 SOP，并保持相同制品和门禁。

所有读取、写入、排他创建与真实路径解析由宿主执行；当前本地测试通过 mock 验证分派与结构拒绝逻辑，不等同于真实宿主集成或沙箱。未知参数、读取失败、缺少证据、重复结果和覆盖不闭合先走有限回流（初次+2 次修复尝试，携带具体原因重问同一实例）；仍失败、路径逃逸、权限问题或同错复发返回 blocked，并保留本次已有黑板与已 confirmed 的结论。

## 11. 与 Dev Companion 的边界

本团队持续保持只读分析职责，不承担实现、发布或开发完成度验收。Dev Companion 可把其报告作为“已有项目分析”的证据输入；`complete` 仅表示本次分析结构闭合，不代表产品需求完成、测试通过或软件可上线。

不自动写 `.toh/memory` 或任何全局记忆。只有用户明确要求时才在其指定位置保存额外记忆；运行记录已在独立黑板中保留。
