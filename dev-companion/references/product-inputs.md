# 产品与可行性输入契约

本文件是 companion-product 角色与用户共同引用的契约：需求例子按下面的最小结构编写和核对。示例仅演示结构，所有内容必须替换为真实事实；示例文字不证明发生过用户确认或真实调查。

## 需求例子的最小结构

每个需求例子对应一个功能，四段缺一不可：

| 字段 | 含义 | 填写规则 |
|---|---|---|
| 用户故事 | 作为谁，在什么场景，希望做什么 | 描述真实使用者与场景，不写实现方式 |
| 验收标准 | 怎么算完成 | 每条可独立核验：写明具体输入与预期结果；不写"界面友好"之类无法核验的话 |
| 非目标 | 明确不做什么 | 显式列出容易混淆的相邻能力，防止范围蔓延 |
| 调查项 | 依赖的现有实现或外部能力 | 每项带证据来源（文件路径、命令输出、官方文档）；未调查的标 `investigation_required`，不留空也不删 |

不确定、需要用户决定的事项不塞进例子，单独列入 open_questions 并附建议选项；业务取舍由用户确认，不由角色代答。

## 完整示例

沿用支出合计工具，为其新增"导出 CSV"功能。内容为结构演示，真实使用时替换为实际调查结果。

| 字段 | 内容 |
|---|---|
| 用户故事 | 作为只在本机记账的用户，我在得到合计后，希望把明细导出为 CSV 文件，以便用表格软件打开 |
| 验收标准 | 1. 输入 [20, 30]，导出文件包含两行明细与一行合计 50；2. 文件可被标准 CSV 解析（逗号分隔、UTF-8）；3. 空列表导出仅含表头与合计 0 |
| 非目标 | 不做 Excel/xlsx 格式；不做定时自动导出；不弹系统文件选择对话框（首版固定输出路径） |
| 调查项 | 1. 现有 `total_expenses` 与明细数据结构——已读 ledger.py 第 12–18 行，返回 (items, total)，证据：真实代码路径与行号（confirmed）；2. Python 标准库 csv 可写 UTF-8 文件——证据：官方文档 csv 模块页（confirmed）；3. 表格软件对无 BOM UTF-8 的兼容性——未在本机验证（investigation_required） |

对应 open_questions：输出文件名是否需要用户可配置？（建议首版固定为 expenses.csv）

## 与角色的关系

companion-product 按本结构产出与核对需求例子，用户对字段内容的修改即构成新的需求输入；主会话负责把确认后的范围记入规划。companion-checker 逐条核对接应的验收标准；任何一条改为"已完成"前，其调查项不得停留在 investigation_required，除非该缺口已明示给用户并由用户接受。
